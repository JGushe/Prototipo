1. INTRODUCCIÓN Y OBJETIVO DEL SISTEMA
================================================================================

El sistema desarrollado es una aplicación móvil para Android cuyo propósito es
integrar dos funcionalidades principales:

  1. Gestión de tareas y recordatorios.
  2. Monitoreo del uso del dispositivo (tiempo en pantalla, aplicaciones más
     utilizadas y número de desbloqueos).

Adicionalmente, el sistema genera recomendaciones automáticas basadas en
reglas simples que combinan la carga de tareas pendientes con los patrones de
uso detectados.

REQUISITOS FUNDAMENTALES QUE GUIARON EL DESARROLLO:
  - Plataforma: Solo Android, versión 10 o superior.
  - Framework: Flutter (Dart) para interfaz y lógica principal.
  - Gestión de tareas: Crear, editar, eliminar y listar tareas locales.
  - Recordatorios: Notificaciones locales programadas por tarea.
  - Monitoreo: Tiempo de pantalla diario, apps más usadas, desbloqueos,
    mediante UsageStatsManager (API nativa de Android).
  - Dashboard: Pantalla de resumen con métricas y gráficos.
  - Recomendaciones: Motor de reglas simples.
  - Base de datos: SQLite local, sin nube.
  - Privacidad: Todos los datos permanecen en el dispositivo.

DECISIÓN CLAVE DE PRIVACIDAD:
  Se eligió SQLite local (paquete sqflite) en lugar de una base de datos en la
  nube (como Firebase) porque el requisito explícito del proyecto establece
  que "todos los datos permanecen en el dispositivo; no se comparten
  externamente". Esta decisión también simplifica el prototipo al no requerir
  configuración de servidores ni cuentas externas.

================================================================================
2. ARQUITECTURA GENERAL DEL SISTEMA
================================================================================

El sistema sigue una arquitectura en capas (Clean Architecture simplificada)
organizada en cuatro carpetas principales dentro de lib/:

  lib/
  ├── main.dart        -> Punto de entrada y navegación principal
  ├── models/          -> Modelos de datos (estructuras de las entidades)
  ├── database/        -> Acceso a base de datos SQLite
  ├── services/        -> Lógica de negocio (uso, notificaciones, reglas)
  └── screens/         -> Interfaz gráfica (pantallas)

Esta separación permite que la interfaz gráfica (screens) no dependa
directamente de la base de datos, sino que use los servicios como
intermediarios. Esto facilita el mantenimiento y la evolución del sistema.

3.5 FASE 4: MODELOS DE DATOS
--------------------------------------------------------------------------------
Se crearon tres modelos de datos (clases Dart) que representan las entidades
del sistema. Cada modelo tiene dos funciones principales:

  - toMap():   Convierte el objeto a un mapa (diccionario) para guardarlo en
               SQLite.
  - fromMap(): Reconstruye el objeto desde un mapa leído de SQLite.

MODELO 1: Tarea (lib/models/tarea.dart)
  Variables:
    id               -> Identificador único (auto-generado por SQLite)
    titulo           -> Título de la tarea (obligatorio)
    descripcion      -> Descripción opcional
    fechaCreacion    -> Fecha en que se creó la tarea
    fechaVencimiento -> Fecha/hora límite (para programar el recordatorio)
    completada       -> Booleano: si la tarea está hecha o no
    prioridad        -> 'alta', 'media' o 'baja'

  Por qué estas variables:
    - La prioridad permite al motor de recomendaciones detectar tareas
      urgentes.
    - La fecha de vencimiento permite programar notificaciones de recordatorio.
    - El campo completada permite filtrar tareas pendientes vs. hechas.

MODELO 2: UsoPantalla (lib/models/uso_pantalla.dart)
  Variables:
    id                  -> Identificador único
    fecha               -> Fecha del registro (1 registro por día)
    tiempoTotalMinutos  -> Tiempo total de pantalla en minutos
    numeroDesbloqueos   -> Cantidad de desbloqueos del día
    appMasUsada         -> Nombre de la app más usada
    tiempoAppMasUsada   -> Minutos en la app más usada

  Por qué estas variables:
    - Se guarda UN registro por día para poder construir la métrica semanal.
    - El tiempo total en minutos es la métrica principal de "uso de pantalla".
    - La app más usada sirve para el dashboard y para detectar redes sociales.

MODELO 3: Recomendacion (lib/models/recomendacion.dart)
  Variables:
    id       -> Identificador único
    fecha    -> Fecha/hora en que se generó
    tipo     -> 'pausa', 'alerta_uso', 'sugerencia_foco', 'descanso'
    titulo   -> Título corto de la recomendación
    mensaje  -> Texto completo del consejo
    leida    -> Booleano: si el usuario ya la leyó

  Por qué estas variables:
    - El tipo permite mostrar un ícono y color distinto por categoría.
    - El campo leida permite resaltar recomendaciones no leídas.

3.6 FASE 5: BASE DE DATOS SQLite
--------------------------------------------------------------------------------
Se implementó la base de datos en lib/database/database_helper.dart usando el
patrón Singleton (una única instancia compartida por toda la app).

Se crearon 4 tablas:

  TABLA             PROPÓSITO
  tareas            Gestión de tareas (1 fila por tarea)
  uso_pantalla      Métrica diaria de uso (1 fila por día)
  app_uso           Uso por aplicación individual
  recomendaciones   Recomendaciones generadas por el motor de reglas

FUNCIONES DE LA BASE DE DATOS (DatabaseHelper):

  - database (getter):     Abre o devuelve la conexión a SQLite.
  - _createDB():           Crea las 4 tablas al iniciar por primera vez.
  - insertarTarea():       Guarda una tarea nueva.
  - obtenerTareas():       Lista tareas (filtrables por completada).
  - actualizarTarea():     Modifica una tarea existente.
  - eliminarTarea():       Borra una tarea por su id.
  - insertarOActualizarUsoPantalla(): Guarda o actualiza el uso del día.
  - obtenerUsoSemanal():   Devuelve los últimos 7 días de uso.
  - obtenerUsoHoy():       Devuelve el uso del día actual.
  - insertarRecomendacion(): Guarda una recomendación.
  - obtenerRecomendaciones(): Lista recomendaciones (filtrables por leída).
  - marcarRecomendacionLeida(): Marca una recomendación como leída.
  - close():               Cierra la conexión a la base de datos.

3.7 FASE 6: SERVICIOS (LÓGICA DE NEGOCIO)
--------------------------------------------------------------------------------

SERVICIO 1: UsoPantallaService (lib/services/uso_pantalla_service.dart)
  Funciones:
    - solicitarPermisoUso(): Solicita el permiso PACKAGE_USAGE_STATS.
    - solicitarPermisoNotificaciones(): Pide permiso de notificaciones.
    - _nombreApp(): Obtiene el nombre legible de una app desde su paquete.
    - capturarUsoDelDia(): Consulta UsageStatsManager y guarda el uso del día.
    - obtenerTopAppsDelDia(): Devuelve las 5 apps más usadas.

  Por qué se usó la API nativa:
    - El paquete usage_stats envuelve UsageStatsManager de Android, que es
      la fuente oficial de datos de uso. Es Android-only y requiere el
      permiso especial PACKAGE_USAGE_STATS que el usuario activa manualmente
      en Ajustes del dispositivo.

SERVICIO 2: NotificacionService (lib/services/notificacion_service.dart)
  Funciones:
    - init(): Inicializa el plugin de notificaciones y pide permisos.
    - programarNotificacionTarea(): Programa un recordatorio 30 minutos antes
      de la fecha de vencimiento de una tarea.
    - enviarNotificacion(): Envía una notificación inmediata.
    - cancelarNotificacion(): Cancela una notificación por su id.
    - cancelarTodas(): Cancela todas las notificaciones.

SERVICIO 3: MotorRecomendaciones (lib/services/motor_recomendaciones.dart)
  Función principal:
    - evaluarYGenerar(): Evalúa las reglas y genera recomendaciones.

  Reglas implementadas:
    REGLA 1: Si el uso total de pantalla supera 4 horas (240 min)
             -> recomendar descanso.
    REGLA 2: Si hay más de 5 tareas pendientes
             -> sugerir priorizar y dividir.
    REGLA 3: Si una red social (Facebook, Instagram, WhatsApp, etc.)
             supera 30 minutos -> sugerir pausa de 15 minutos.
    REGLA 4: Si hay tareas de alta prioridad sin completar
             -> sugerir técnica Pomodoro.
    REGLA 5: Si hay más de 3 horas de uso Y más de 3 tareas pendientes
             -> sugerir modo enfoque.

3.9 FASE 8: PROBLEMAS DE DEPENDENCIAS Y COMPILACIÓN
--------------------------------------------------------------------------------

PROBLEMA 5: Versiones de paquetes incorrectas.
  Síntoma: "device_apps ^0.2.0 which doesn't match any versions"
  Causa:   Varias versiones en pubspec.yaml no existían.
  Solución:
    - Consultar pub.dev para obtener versiones reales.
    - Corregir: usage_stats -> ^2.0.1, flutter_local_notifications -> ^22.3.0,
      timezone -> ^0.11.1, permission_handler -> ^13.0.1, fl_chart -> ^1.2.0.
    - Eliminar device_apps (descontinuado) y reemplazarlo por la API nativa
      UsageStats.getAppInfo().
    - Eliminar app_usage (no se usaba).

PROBLEMA 6: Cambio de API en flutter_local_notifications v22.
  Síntoma: Errores de "named parameter required" y "too many positional args".
  Causa:   La v22 cambió de parámetros posicionales a parámetros nombrados.
  Solución:
    initialize(settings: ...) en vez de initialize(...).
    zonedSchedule(id:, title:, body:, scheduledDate:, notificationDetails:).
    show(id:, title:, body:, notificationDetails:).
    cancel(id: id).

PROBLEMA 7: permission_handler requiere compileSdk 37.
  Síntoma: "requires ... compile against version 37 or later".
  Causa:   permission_handler 13.0.1 usa permission_handler_android 14.0.0
           que requiere SDK 37, pero AGP 9.1.0 soporta máximo SDK 36.
  Solución:
    - Bajar permission_handler de ^13.0.1 a ^12.0.3 (que usa
      permission_handler_android 13.0.1, compatible con SDK 36).

PROBLEMA 8: flutter_local_notifications requiere desugaring.
  Síntoma: "requires core library desugaring to be enabled".
  Causa:   El paquete usa APIs de Java 8+ que requieren desugaring.
  Solución (en build.gradle.kts):
    - Agregar isCoreLibraryDesugaringEnabled = true.
    - Agregar la dependencia coreLibraryDesugaring("com.android.tools:
      desugar_jdk_libs:2.1.4").
    - Habilitar multiDexEnabled = true.

PROBLEMA 9: Conflicto de archivos Gradle (Groovy vs Kotlin DSL).
  Síntoma: Archivos duplicados .gradle (antiguos) y .gradle.kts (nuevos).
  Causa:   La estructura manual inicial usaba Groovy, pero Flutter 3.47.1
           genera Kotlin DSL.
  Solución:
    - Ejecutar "flutter create ." para generar archivos faltantes.
    - Eliminar los archivos Groovy antiguos (build.gradle, settings.gradle,
      app/build.gradle).
    - Conservar los Kotlin DSL (.kts).
    - Establecer minSdk = 29 (requisito Android 10+).

PROBLEMA 10 (menores, corregidos por flutter analyze):
  - withOpacity() deprecado -> reemplazado por withValues(alpha:).
  - value: deprecado en DropdownButtonFormField -> reemplazado por
    initialValue:.
  - Campo _titulos sin usar -> eliminado.
  - Imports sin usar -> eliminados.
  - Uso de BuildContext tras await -> agregado chequeo ctx.mounted.
